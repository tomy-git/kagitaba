# kagitaba

[English](README.md) | [日本語](README.ja.md)

`kagitaba` は、macOS 向けの**実験的な**ローカルファースト API キー管理 CLI ツールです。

API キーをローカルの macOS **ログインキーチェーン（Login Keychain）** に保存し、明示的に指定して起動したコマンドに対してのみ、選択したキーを環境変数として渡します。

> ⚠️ セキュリティ上の注意
>
> - 本プロジェクトは実験段階であり、独立した第三者によるセキュリティ監査は**受けていません**。
> - `kagitaba run` で起動したコマンドおよびその子プロセスは、渡されたキーの値を読み取ることができます。
> - 同一ユーザー権限で動作する悪意あるプログラムから、秘密情報を隔離・保護するものではありません。
> - 起動した子プログラム自身のログ、標準出力、クラッシュレポートなどから秘密情報が漏洩する可能性があります。

## 提供機能

- `kagitaba set <ENV_NAME>`
  - エコーバック（入力内容の表示）を行わない安全なプロンプトで秘密情報を入力します。
  - コマンドライン引数としての秘密情報の指定は受け付けません。
  - 既存のキーを上書きする前に確認を求めます。
  - 入力待ちの間に別プロセスによって同名キーが登録された場合も、上書き確認を求めます。
- `kagitaba status [ENV_NAME]`
  - 登録状況またはキー名のみを表示します。
  - 秘密情報の値自体は一切出力しません。
- `kagitaba run --key <ENV_NAME> [--key <ENV_NAME>...] -- <PROGRAM> [ARGS...]`
  - 指定したキーのみをキーチェーンから読み込みます。
  - 子プロセスを直接実行します（シェルを介したコマンド文字列の評価は行いません）。
  - 子プロセスの終了ステータスコードをそのまま引き継ぎます。
- `kagitaba delete <ENV_NAME>`
  - 削除前に確認を求めます。
  - `kagitaba` が管理する項目のみを削除します。

## インストール

[mise](https://mise.jdx.dev/) がインストールされている環境では、次の手順でビルドできます。

```bash
mise trust mise.toml
mise install
mise exec -- cargo build --locked --release
```

実行バイナリは `target/release/kagitaba` に生成されます。

`mise.toml` は Rust のバージョンを固定し、Cargo、rustfmt、Clippy をインストールします。Rustup と Cargo のツールチェーンおよび依存関係のキャッシュは、本作業ツリー内の（Git 管理対象外である）`.local/` ディレクトリに保存されます。シェルの起動設定やシステム全体の Rust 設定は変更しません。なお、mise 自体のインストール追跡情報、信頼設定、キャッシュは作業ツリーの外部に保存されます。

開発用コマンドは、プロジェクト専用のパスを適用するために `mise exec --` 経由で実行してください。すでに互換性のある Rust 環境が整っている場合は、その環境で直接ビルドすることも可能です。

mise の共有管理情報は本作業ツリー内の Rust 環境を参照します。そのため、作業ディレクトリを移動した場合や、同じ Rust バージョンを使用する別の作業ツリーで作業する場合は、移動先で再度 `mise install` を実行してください。Cargo および Rustup の関連ファイルは、作業ツリーごとに独立して保持されます。

## 使い方

キーの登録:

```bash
kagitaba set OPENAI_API_KEY
```

指定したキーの登録状況を確認:

```bash
kagitaba status OPENAI_API_KEY
```

登録済みキー名の一覧表示:

```bash
kagitaba status
```

選択したキーを環境変数として渡してコマンドを実行:

```bash
kagitaba run --key OPENAI_API_KEY --key ANTHROPIC_API_KEY -- curl https://example.com
```

キーの削除:

```bash
kagitaba delete OPENAI_API_KEY
```

## 操作履歴

ファイルへの履歴保存は既定では無効です。明示的に有効化してください。次の
履歴管理コマンドは Keychain にアクセスしません。

```bash
kagitaba history enable
kagitaba history config
kagitaba history config --retention-days 30 --max-events 10000
kagitaba history --key OPENAI_API_KEY --failed --limit 20
kagitaba history disable
kagitaba history clear
kagitaba history reclaim
```

`history` は新しい操作から順に表示します（既定50件、指定範囲1〜1000件）。
`--key` と `--failed` は併用できます。失敗には登録・更新・削除の失敗、起動前の
失敗、子プロセスの非ゼロ終了とシグナル終了を含みます。ユーザーによる中止や
結果不明を失敗と推定しません。日時は UTC（`Z`）で表示します。

新規登録・更新・削除の結果、検証済みのキー名、固定のエラー分類、操作IDで
関連付けた run の起動・終了を記録します。プログラムはファイル名だけを記録し、
パス全体、引数、環境変数の値、秘密入力、子出力、生のエラー文は保存しません。
`status` は履歴へアクセスしません。256バイトを超えるキー名や、制御文字を
エスケープした後に256バイトを超えるプログラム名は履歴から省略しますが、
本来のキー操作やコマンド実行は継続します。

run の開始は、選択したキーを渡す子プロセスの生成が成功した後だけ記録します。
API 呼び出し、認証成功、実際のキー利用を保証しません。終了記録のない開始は
`unknown`（結果不明）、開始記録のない終了は `end-only` と表示します。終了コード
とシグナルは区別し、終了コード143とシグナル15も別に表示します。終了待機の
失敗は終了状態不明です。履歴はローカルのベストエフォートな記録であり、異常終了
や保存障害で記録漏れが起き得ます。同一ユーザーによる改変・削除を防ぐ監査証跡
ではありません。

保存先は macOS の `$HOME/Library/Application Support/kagitaba/`、Linux テスト
ビルドの `$HOME/.local/state/kagitaba/` です。所有ユーザーの専用ディレクトリは
0700、DB・設定・ロック・一時ファイル・SQLite 関連ファイルは0600で扱います。
不適切な所有者・権限、シンボリックリンク、ハードリンク、通常ファイル以外は
自動修復せず拒否します。履歴にはキー名・プログラム名・利用時刻という情報が
残ります。バックアップも同じ権限で保護してください。自動バックアップや
外部へのログ送信は行いません。

保持の既定値は90日・10,000**イベント行**です（通常の run は開始・終了の2行）。
設定範囲は1〜3650日・2〜1,000,000行です。記録・一覧時に、操作IDのグループを
まとめて削除し、期間判定にはグループ内の最新時刻を使います。設定を縮小した
場合も次の記録・一覧で反映します。未使用時のバックグラウンド削除はありません。
無効化しても既存履歴は保持し、一覧・消去・容量回収を利用できます。

`history clear` は `y` または `yes` の確認後、履歴だけを削除して SQLite の
`VACUUM` を実行します。設定と Keychain 項目は保持します。論理削除後の容量回収
だけが失敗した場合は、履歴は消去済みであることをエラーで明示します。
`history reclaim` で再試行できます。保持制限による削除は論理削除です。
`reclaim` は未使用ページを回収し、DB容量の約2倍の空き容量が必要になる場合が
あります。バックアップ、ファイルシステムのスナップショット、記憶媒体からの
完全消去は保証しません。[履歴ストレージの詳細](docs/history.md) にスキーマと
障害時の扱いを記載しています。

記録失敗時は stderr に固定文 `warning: operation history could not be recorded.`
だけを表示します。キー操作が成功した場合は通常の成功表示を保ち、履歴障害で
子プロセスの終了コードを変えたり、Keychain 操作を巻き戻したりしません。
ロック待機には上限があります。ディスク不足・権限不足・初期化失敗・DB破損でも
本来の操作結果を維持し、壊れたDBや未対応スキーマを自動削除・上書きしません。
履歴管理コマンド自体の失敗は固定文のエラーで返します。DBの内容が破損していても、
ファイル属性と設定が安全なら `history disable` で記録を停止できます。
中断された run は結果不明として残る場合があります。

## アーキテクチャ

各層を独立してテストできるよう、モジュールを分割しています。

- `src/cli.rs`: CLI 引数のパースとコマンド構造の定義
- `src/store.rs`: 認証情報ストアのインターフェースとプラットフォーム別実装
  - macOS: `security-framework` バインディングを使用し、専用のサービス名前空間に保存
  - macOS 以外: モックを用いたテストを可能にするため、実際の保存・取得機能を持たないプレースホルダーのバックエンドを使用
- `src/process.rs`: 子プロセスの実行（プログラム、引数、スコープを限定した環境変数の注入）
- `src/app.rs`: コマンドの統括、プロンプト表示、入力バリデーション、ユーザー向け挙動の制御
- `src/history/`: 型で限定したイベント、専用 SQLite 保存、設定、照会

## キーチェーンとプラットフォームの動作

- 保存先にはローカルのログインキーチェーンを使用し、`kagitaba` 専用のサービス名前空間に格納します。
- キーチェーンのロックポリシーや自動ロック、スリープ時のロック設定を変更することはありません。
- キーの未登録、アクセス拒否、キーチェーンのロック、プロセスの起動失敗など、想定されるエラーが発生した場合は、秘密情報の値を露出させることなくエラーとして返します。
- 無効なコマンドライン引数が渡された場合、その値をエラーメッセージに出力（エコーバック）せずに拒否します。なお、ヘルプやバージョンの表示は通常どおり利用可能です。
- 新規登録時に既存の項目を上書きすることはありません。ユーザーが上書きを確認した場合にのみ既存項目を更新します。更新前に対象項目が削除されていた場合は、新規作成を行わずに処理を失敗させます。
- キー名はキーチェーン項目の属性情報から取得します。秘密情報の値を読み取ったり、別のインデックスを管理したりすることはありません。旧形式のインデックス用項目は無視されます。
- 子プロセスは親プロセスの環境変数を通常どおり継承した上で、選択されたキーを追加または上書きします。既存の環境変数をフィルタリング（除外）することはありません。
- アプリケーションが保持する秘密情報のバッファは、ドロップ（解放）時にゼロクリアされます。ただし、Rust のプロセス API や OS がメモリ上に別のコピーを保持している可能性があるため、メモリからの完全な消去を保証するものではありません。

### シグナルの扱い

`kagitaba run` は子プロセスの終了コードをそのまま返します。Unix シグナルによって終了した場合は、シェルと同様に `128 + シグナル番号` を返します。

## コード署名とアップグレード

macOS のキーチェーンアクセス許可は、実行ファイルの識別情報（署名）やファイルパスに関連付けられる場合があります。そのため、バイナリの差し替えやアップグレード後に、キーチェーンへのアクセス許可ダイアログが再度表示される可能性があります。

管理された環境で安定して利用するには、一貫したコード署名と配布運用を行ってください。

## 開発

```bash
mise exec -- cargo fmt --all -- --check
mise exec -- cargo clippy --locked --all-targets -- -D warnings
mise exec -- cargo test --locked --all-targets
```

既定のテストは擬似的な認証情報とモックを使用するため、実際のログインキーチェーンにはアクセスしません。テストでは、呼び出し履歴を記録するフェイク実装による確認プロンプトや失敗パスの検証、キーチェーン検索クエリの構築やキー名の抽出処理、およびバイナリレベルでの引数エラー出力などを検証します。

macOS には、通常実行では除外される一時 Keychain の統合試験があります。専用の一時ディレクトリに使い捨ての Keychain を作り、擬似的な値でネイティブアダプターを検証し、成功時やアサーション失敗時に削除します。明示的に選択した一時 Keychain だけを使用し、ログインキーチェーンは開きません。次のコマンドで実行します。

```bash
mise exec -- cargo test --locked --lib store::keychain::integration::isolated_keychain_round_trip -- --ignored --exact --test-threads=1
```

測定コマンド、カバレッジ結果、未実行経路は [テストとカバレッジ](docs/testing.md) を参照してください。実 OS のアクセス拒否や取消は、ログインキーチェーンの状態を変更せず、OS 呼び出し境界のフェイクで検証します。

### CI

GitHub Actions は、PR、`main` への push、手動実行で動作します。作業ブランチへの push だけでは CI を開始しません。同じイベントと ref に対する新しい実行が始まると、古い実行をキャンセルします。

GitHub-hosted macOS ランナーの割り当て不足のため、CI は当面 Ubuntu のみで実行します（[Issue #6](https://github.com/tomy-git/kagitaba/issues/6)）。SPDX ライセンス検査とその Python テスト、`mise.toml` の固定 Rust バージョンの読み取り、フォーマット確認を維持し、Clippy と Rust テストは `--locked` を付けて実行します。Cargo の依存関係とビルド成果物は OS・アーキテクチャ・コンパイラごとに分け、マニフェストとワークフローに基づくキーでキャッシュします。キャッシュに一致した場合も、Clippy とテストは毎回実行します。

Linux CI では、macOS ネイティブの Keychain アダプターや macOS 限定テストを検証できません。macOS 固有の変更は、ローカルの Mac で上記の開発用コマンドを実行し、Clippy とテストの結果を記録してください。通常のテストはモックと擬似的な認証情報を使用し、実際のログインキーチェーンにはアクセスしません。Keychain 統合試験の拡充は [Issue #4](https://github.com/tomy-git/kagitaba/issues/4) で管理します。

GitHub-hosted macOS ランナーの割り当てが安定した時点、または適切な代替ランナーを確保した時点で、macOS CI の復帰を検討します。この暫定対応では self-hosted runner を導入しません。
